# Tenant subscription billing

New tenants without an assigned plan can select a configured plan and request their first paid month. Tenant finance/admin users can also request a manual one-month renewal of the currently assigned plan. The flow uses whichever voucher collection gateway is active in Platform Control Settings (OBPay, PawaPay, or ioTec), but writes only to the dedicated subscription invoice, attempt, and history tables. It does not create voucher-sale transactions, credit tenant wallets, or issue vouchers.

“Separate money” here means separate application accounting on the same configured merchant account. It does **not** create a separate provider wallet, settlement account, or bank balance. Provider callbacks do not prove subscription payment; a tenant status check performs an authenticated provider lookup and compares the attempt reference, amount, and UGX currency before applying an entitlement. The adapter stores a provider/account fingerprint and environment on the attempt so later gateway configuration changes cannot silently verify an attempt against a different account. Raw credentials and phone numbers are not stored in subscription history.

Checkout remains explicitly default-off (`SUBSCRIPTION_CHECKOUT_ENABLED=false`). Configure and verify the active voucher gateway in Platform Control Settings, then set the flag to `true` in the intended environment to allow new subscription collections. Existing voucher configuration by itself does not enable subscription charges. Do not edit production settings or run database migrations as part of local development. The provider contract has been confirmed by the product owner; the feature tests use mocked provider responses and are not a live settlement test.

Quotes are encrypted, tenant-bound, short-lived, and require explicit consent. Prices are whole-number UGX only; plan or amount changes invalidate the quote. The user’s request is idempotent, a provider request is made only after the invoice/attempt commit, and an ambiguous submission is never retried automatically. OBPay hosted checkout is accepted only from its HTTPS checkout host; its URL is encrypted at rest and shown only while the invoice is open. Only an authenticated lookup with an exact reference, amount, currency, and recognized status may settle an invoice. A newly selected plan is assigned only after verified payment; payment while suspended, after an admin changes the plan, or for a removed plan requires review. Admin plan changes lock the tenant and move unresolved invoices to review. Renewals are not recurring, and later plan switches remain admin-controlled.

Invoices are tenant-scoped and printable from the billing history page (browser print / Save as PDF). Billing status and invoices are separate from voucher sales and wallet reporting. Legacy/manual payments are not imported as provider-verified subscription payments.

Remaining operational work includes a platform-admin resolution workflow for invoices in review, safe recovery/retry after ambiguous starts, refund/reversal and dispute handling, production-engine concurrency testing, and database-enforced immutable audit history. Unresolved invoices deliberately block another charge until resolved. No webhook, scheduler, automatic renewal, or automatic account suspension is part of this flow. The isolated `CollectionPurposeRouter` and `IsolatedCollectionMappingStore` prototypes remain unused; they are not required for this app-ledger separation and must not be deployed as a payment-routing mechanism.
