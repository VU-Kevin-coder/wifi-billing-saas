# Paid-sale fulfillment (draft)

This change is stacked on PR #40. Do not deploy it without independent financial, database and operations review.

After an existing provider-specific verification succeeds and the existing validation passes, the confirmation transaction locks the tenant's sale, marks it completed, credits the operator wallet and inserts a unique `sale_fulfillment_work` row. The wallet credit has a new unique sale-credit key; no old ledger rows are backfilled. All three writes commit or roll back together. `completed` now means payment confirmed, not access active. Token-based payment status returns `fulfillment_pending` when no voucher exists; provisioning and activation are reported separately. A confirmation-time package fingerprint blocks retries if package attributes subsequently change; this is **not** a purchase-time terms snapshot.

The immediate attempt is an optimization, not a queue dependency. The scheduled command `payments:retry-fulfillment` reads only explicitly recorded work, at most 25 due rows per run. Claims have five-minute leases; expired leases can be recovered following a process crash. Failures are logged by tenant and transaction ID and exception class (not raw provider/customer payloads); retry is delayed five minutes and stops after 10 claims, including crash claims. `status`, `attempts`, `next_attempt_at`, `last_error_class` and timestamps support operational inspection. Exhaustion is logged both after the final failed attempt and after an expired final lease. An authorized platform operator can run the read-only `php artisan payments:inspect-exhausted TENANT_ID --limit=25` to see a tenant-scoped count and up to 100 work IDs, transaction IDs, attempt counts, error classes and update times. It does not reveal customer phone numbers or error messages, retry work, or resolve cases; the displayed count may exceed the row limit. The scheduler must actually be running and logs monitored. There is no operator UI, alert, or supported requeue action in this draft; exhausted items require investigation and a separately designed safe remediation procedure. Customers currently continue to see fulfillment pending on exhaustion, so they must be directed to support; no customer-facing escalation is implemented. Do not blindly reset rows or replay historic sales.

Fulfillment locks the work row and sale, creates at most one sale-linked voucher using existing DB uniqueness, and runs existing activation logic in the same database transaction. Site-agent provisioning commands and RADIUS behavior remain in the existing activation service. A receipt is best effort after commit, is not part of the durable worker, and is not sent for a provisioning session. A crash after commit can lose the receipt. Neither router execution nor access activation is represented as completed merely because work has been issued: the status endpoint checks the session.

Limits requiring follow-up: existing provider verification still relies on live package data and can reject an otherwise paid order if the package or required details disappeared/changed before verification; this change does not invent provider reconciliation or capture a purchase-time snapshot. If the database cannot commit, confirmation cannot be persisted. Existing reconciliation/provider submission limitations remain. Simulator mode is gated to local/testing as before. Legacy completed sales do not acquire work or get automatically replayed. Verify refund/chargeback policies for a credited but unfulfilled sale, package deletion/edit behavior, lease timing, monitoring and receipt delivery before release. The automated tests simulate a lost worker lease and verify sequential duplicates; they do not prove simultaneous race behavior or a real process kill. Database uniqueness and row locks are defense in depth, not a substitute for concurrency tests.
