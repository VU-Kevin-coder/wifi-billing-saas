# Production security launch gate\n\n## Audit basis\nReviewed `main` at `9d1413bb0a8e8b85dbf75d5f1921e8f2a21d78da` on 7 November 2026. This is a review aid, not proof that production configuration is safe. Do not record secrets in this file.\n\n## What changed since the previous audit\n\n- The current baseline adds a site-agent architecture and a large operational change set. The site agent is protected by a bearer-token middleware.\n- The payment path now includes direct MTN MoMo/Airtel Money work and a pending-payment reconciliation command with feature coverage.\n- Payment simulation is fail-closed in the reviewed code: its config default is `false`; both the simulated fulfilment path and sandbox success route also require `local` or `testing`.\n- Tenant-owned Eloquent models use a global tenant scope and the documented tenant context is derived from the authenticated user rather than request input.\n\n## Highest-priority remediation: make production fail closed before any live router or payment activation\n\nThe main remaining risk is deployment drift: a safe code path can still become unsafe when optional agent routing, router transport, or payment settings are enabled in production without an explicit launch check. The safest next change is a small, reversible *production readiness guard* that blocks the risky action rather than guessing.\n\n### Acceptance criteria\n\n1. On `production`, refuse payment fulfilment unless simulation is disabled and the real provider credentials/configuration validate.\n2. On `production`, refuse site-agent router actions unless `SITE_AGENT_REQUIRED=true` and an authenticated, scoped agent is present.\n3. Refuse direct router connections unless encrypted transport is explicitly enabled; router credentials must remain site-local.\n4. Cover each refusal with feature tests, including a test proving no voucher is issued and no router command is sent.\n5. Log a redacted security event for each blocked attempt; never log tokens, router passwords, or payment secrets.\n\n## Safe rollout plan\n\n- Implement the guard behind a default-on production check, with no database migration and no credential rotation.\n- Run the existing payment and tenant feature tests plus new negative-path tests.\n- Deploy with the guard in report-only mode first if the environment supports it; inspect redacted logs for expected configuration gaps.\n- Switch enforcement on only after the production configuration is confirmed. Rollback is the single feature/config flag, not a data rollback.\n\n## Release decision\n\n**Do not enable live payment fulfilment or router provisioning until the five acceptance criteria above pass in the deployment environment.**\n\nThe existing simulation guard is good news, but it is not a substitute for validating the live agent/router boundary.\n
