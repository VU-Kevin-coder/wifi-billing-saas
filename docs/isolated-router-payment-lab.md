# Isolated MikroTik and payment sandbox lab — BLOCKED, not a deployment

Baseline: main `75c5399d2da1e062e5dfece532475c77f588ab64`. This branch adds a loopback-only experimental FreeRADIUS bridge and payment lab safety checks; it does **not** deliver a ready-to-run physical-router deployment. No real router, provider, network, credentials, hosting account, or transaction has been used. Do not use with customers, production devices, production accounts, real money, or real data. An authorized operator must resolve the gates below first. Do not treat test success as production approval.

## Hard blockers

* This integration includes durable payment fulfillment, but online-sale vouchers remain explicitly rejected by RADIUS activation, authorization and accounting. Payment status also withholds the voucher while a RADIUS session is provisioning, so the customer cannot initiate the accounting event needed to make it active. Do not run provider orders for RADIUS. Resolving readiness, refund/revocation races and a reviewed reconciliation/compensation plan is required; payment plus voucher-to-router end-to-end acceptance has not been proven. See `docs/payment-fulfillment-durability.md` and `docs/payment-sandbox-staging.md` for other payment limitations.
* RouterOS attributes and actual packet behavior are unverified. The adapter requires the same `Acct-Session-Id` in Access-Request and accounting, and a stable Event-Timestamp; do not invent them. It listens only on 127.0.0.1. A real device cannot reach this configuration as supplied. Changing listener addresses requires a reviewed private topology, firewall and encrypted transport; the lab files do not provide these.
* No disconnect/CoA sender, accounting outage spool, supported router secret rotation or physical-device tests exist. Admission reserves one identity with database locking, but concurrency and server-database behavior remain unproven. Data-capped and other unsupported policies are rejected; timeout is not a replacement for immediate revocation. Races with refund, revocation, expiry, and backend changes remain. The forward opt-in checks outstanding sessions and commands; reverse changes and races across other paths still need independent review. Never switch a router with active or pending work.
* The normal RouterProvisioningService generates `use-radius=no` and `http-chap`, not a RADIUS recipe; applying it can overwrite router configuration. `HotspotLogin` generates an HTTP IPv4 link, not a proven secure voucher login. A separately reviewed HTTPS portal, device certificate trust, and safe credential flow are prerequisites. Do not bypass certificate warnings or enter voucher credentials over an untrusted link.

## Additional local safeguards — still BLOCKED

Paid RADIUS has **not** been enabled. The circular credential/accounting bootstrap, sale/refund/admission races and revocation remain unresolved; a switch that merely enables sandbox hosts would not isolate credentials or side effects. Do not place a sandbox order or test a physical router yet. A safe design must independently prove a sandbox-only configuration in every process, deterministic tenant/sale/voucher/router bindings, policy and refund checks under a consistent lock order, pre-admission credential transport, callback idempotency, reliable disconnect and operator recovery/compensation. Preserve the existing manual/partial refund semantics for production.

The portal now rejects new purchases for an entire tenant if any router has a RADIUS backend or RADIUS transition marker, including mixed-backend tenants and regardless of `PAYMENTS_SANDBOX_ONLY` or environment. This conservative guard is not a transaction barrier: router settings can change after the check, existing orders can complete, and other initiation routes or direct service calls bypass it. Keep sandbox provider credentials and routes disabled until independent isolation and review. Existing paid orders may still be stranded: status pages say not to pay again and to contact the operator. Operators must reconcile provider status, durable work and refund state manually; never assume an automatic refund. Existing retry exhaustion/blocked work requires operator inspection.

Unsupported pre-issued RADIUS packages (multiple devices, capped or invalid data limit) are rejected before voucher redemption. Authorization checks again; a later package change or concurrent edit can still strand a redeemed voucher. Paid RADIUS sessions, including already-active or ambiguous-router records, are refused by the payment APIs, and both APIs require matching sale and package links. Legacy sales without the new sale link now require manual reconciliation instead of token-based access. The Pesapal callback no longer flashes a voucher: only a browser holding that sale's matching payment token can proceed to the status page. If the browser lost the token, it gets an explicit contact-operator message; no token recovery mechanism is supplied. This changes callback behavior for all providers using that Pesapal path. The local simulation route remains a separate legacy code path and must be disabled. The order guard is not a complete disclosure or race fix for pre-existing data: other delivery mechanisms and the regular site-agent flow still need review, including callback/receipt, policy changes and concurrent refunds. Tests do not prove safety for paid access.

Tests cover rejection with synthetic pending/approved refund records before and after a manually-created RADIUS session, not a real successful paid-RADIUS fulfillment; production refund behavior is not changed. SQLite cannot demonstrate server-database row locking, real concurrent races or deadlock freedom. Duplicate callback tests fake the provider and do not prove live IPN behavior.

## What the guard does — and does not do

`APP_ENV=staging` enables lab restrictions automatically; in other environments, `PAYMENT_LAB_MODE=true` or the legacy `PAYMENTS_SANDBOX_ONLY=true` must be enabled in **every** web and worker process. The guard checks the configured HTTPS host and `sandbox` DB mode in covered MTN, Airtel and Pesapal collection paths and disables automatic provider redirects. Pesapal hosted checkout is blocked in lab mode. Covered Flutterwave requests, withdrawals, manual refund payout approval, simulation and SMS dispatch are also blocked. The guard cannot stop settings changes, live credentials at an approved sandbox host, arbitrary outbound calls, mail, DNS rebinding/proxy behavior, direct DB writes, other code paths or future changes; it is not a firewall. Independently disable unrelated integrations and enforce network isolation. See `docs/payment-sandbox-staging.md` for details. Migrations, config cache, build and startup must be performed only after the deployment target is independently verified. No deployment manifest is supplied because the network, provider callbacks, secured login and router mapping have not been verified.
