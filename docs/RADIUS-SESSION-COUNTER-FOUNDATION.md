# Detached RADIUS generation-counter foundation

`RadiusGenerationCounterDelta` is pure, detached arithmetic. Nothing in the runtime calls it. The local CHR lab can authorize vouchers through FreeRADIUS and logs sanitized accounting observations, but it does not reconcile application sessions, counters, device limits, or disconnect behavior. `RadiusReadiness` is opt-in for the local lab and remains production-gated.

For a caller-proven generation, it adds only the non-negative change in that generation's cumulative input/output to the respective aggregate. A new generation's prior counters must be zero; aggregate totals must include its previous counters and all other generations. Repeating the same counter contributes zero. Missing *both* words of a direction preserves the previous value; a partial pair, non-integer/negative/out-of-range word, regression, inconsistent stored aggregate, or signed-64-bit overflow is rejected without returning an update. Each present direction requires both unsigned 32-bit octets and gigawords; do not manufacture a zero gigaword where it was absent. Even a complete pair is not proof a NAS reported truthfully or did not wrap its full 64-bit counter. An absent direction supplies no evidence of additional usage, so totals may be incomplete. When exact usage is required this must not be treated as proof that a cap has not been reached.

## Why production reconciliation is not wired in

The current disabled accounting path does not safely support multiple devices: a Start replaces application totals with one generation's counters; later events compare generation counters against application totals and replace those totals; a Stop changes the whole application session and clears revocation even if other devices are open. A disconnect request selects only one open generation. Also, ingestion acquires identity/generation before the application session while `requestDisconnect` locks the application session before an accounting generation, creating a lock-order inversion. Fixing just the arithmetic would leave these larger failures intact.

This helper cannot identify duplicate events: unchanged counters yield a zero delta but do not establish event identity, order, freshness, or legitimacy. In particular, a reordered event with higher counters can still pass the arithmetic. It cannot validate a Start, distinguish reused NAS session IDs, prove request-to-Start correlation, reconcile a missing Stop, decide a session's status, or enforce a device limit.

## Requirements before any future integration

- Establish an authenticated, tenant/router-bound generation and robust generation lifecycle, including replay/duplicate handling, strictly ordered evidence, ambiguous IDs and absent or delayed Starts/Stops. Quarantine uncertainty without mutating a different generation. Do not infer Stop from delivery acknowledgment, timeout, or missing accounting.
- Design and enforce a single lock order across *all* paths and revalidate ownership/state after locking. In particular, resolve the current identity/generation versus application-session inversion; address initial identity creation, uniqueness conflicts, deadlocks and retries explicitly. The pure helper takes no locks and cannot make stale snapshots safe.
- Atomically persist the accepted event, per-generation counters, aggregate delta, and any affected outbox records in one transaction; ensure duplicates/replays cannot apply changes twice. Specify incomplete-counter and historical-data/migration behavior before using the helper. Test rollback, overflow, and database-specific integer limits.
- A Stop can terminate only its proven generation. Never mark the overall session disconnected, clear pending revocation, or release another device's capacity merely because one generation stopped. Disconnect and data-cap handling must cover every relevant open generation, with terminal state based on sufficient evidence.
- Design atomic pre-Accept device-slot reservations, correlation from authorization to the right Start, and conservative recovery. Pending or ambiguous reservations must not silently release capacity without evidence. Test simultaneous accepts and Starts on a verified disposable production-like database; SQLite unit tests do not prove row-lock or concurrency behavior.
- Independently review adapter authentication, policy endpoints, session/payment paths and physical-router integration. Keep production readiness and accounting reconciliation disabled until the complete security and correctness prerequisites have been met and reviewed.
