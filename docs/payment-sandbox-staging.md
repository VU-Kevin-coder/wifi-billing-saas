# Collection sandbox staging notes

This branch has only been tested with fakes and isolated SQLite. It has not been tested with any real provider sandbox, production database, concurrent workers or physical router. Do not treat it as deployment approval.

For a controlled payment lab use disposable infrastructure and provider **sandbox-only** credentials. `APP_ENV=staging` enforces lab restrictions automatically even when both switches are false. For a lab with any other `APP_ENV`, set `PAYMENT_LAB_MODE=true` in trusted deployment configuration; the legacy `PAYMENTS_SANDBOX_ONLY=true` also activates all lab restrictions. Never rely on a database setting to turn the guard on. A typo or arbitrary environment name without either flag is not automatically recognized as a lab, so independently verify the effective deployment configuration and restart workers after changes.

The lab permits only the exact configured HTTPS API hosts `sandbox.momodeveloper.mtn.com`, `openapiuat.airtel.africa`, and `cybqa.pesapal.com` for MTN, Airtel and Pesapal respectively, with the corresponding platform environment set to `sandbox`. Automatic redirects are disabled for all of their collection, token and status requests, and non-2xx token/status responses are rejected. The guard checks API hosts, not credentials: sandbox-looking URLs do not make live credentials safe. Network egress restrictions, trustworthy DNS/TLS, disposable data, sandbox credentials, registered sandbox callback/IPN URLs, and independent infrastructure verification remain mandatory. Do not put production secrets, devices or databases in the lab.

No Pesapal checkout host has been independently verified for this deployment, so **all Pesapal checkout redirects are blocked in lab mode**, even if the returned URL looks plausible. A submitted order's tracking ID is retained and the transaction remains pending; never blindly resubmit an ambiguous order. This means a full Pesapal hosted-checkout test is currently unavailable until the exact sandbox checkout destinations and redirect chain are independently verified and safely implemented. Pesapal takes precedence when enabled/configured: disable it when testing MTN/Airtel. MTN sandbox uses EUR request/status amounts while the application expects whole-number UGX package prices; these are test amounts only.

In lab mode payment simulation and its route, Flutterwave requests, withdrawal creation/approval/reconciliation (including manual bank approval), manual refund payout approval, and SMS dispatch are blocked. Other systems such as email, router/site-agent access, manual out-of-band transfers, direct database/network access, and third-party code are not covered by this application guard. Use independent network isolation and disable unrelated live integrations, including mail; do not mistake this guard for a firewall. `SITE_AGENT_REQUIRED=true` is necessary for router-backed tests: when false the existing activation logic can create an `active` session without a router, which is not evidence of actual access.

Confirmation/credit and durable work commit together; fulfillment uses leases and bounded retries. Pending refund requests pause unfulfilled sales without consuming retry attempts; rejection/cancellation permits a later retry. Any approved refund before fulfillment blocks it for manual review, including partial refunds. Inspect blocked rows with `php artisan payments:inspect-exhausted TENANT_ID --blocked`; exhausted rows use the same command without `--blocked`. No supported automated requeue exists. Refunds are manual payouts, not provider-integrated; post-refund access revocation remains best effort. Inspect all unresolved cases before a test continues.

Important remaining limitations: no purchase-time immutable terms snapshot; changed/deleted packages before confirmation can prevent recording a valid provider payment, and changed terms after confirmation block fulfillment. Ambiguous Pesapal submissions without an order tracking ID require manual provider reconciliation and must not be blindly resubmitted. Failed-to-success transitions are not automatically resurrected; investigate conflicting results. Existing legacy completed sales are not automatically replayed. Credentials, webhook contracts, real sandbox checkout/callbacks, scheduler operation, MySQL/PostgreSQL migration and lock behavior, simultaneous duplicate/refund races, crash recovery, gateway reconciliation, post-refund revocation and physical access all require independent testing/review. No automatic chargeback handling is implemented.
